## 2. 你特别问到的几点

**`Stop-ProcessesUsing` 会不会误杀用户自己的 Edge / Chrome？** 基本不会（读代码）：它只处理进程名为 `msedge.exe` / `chrome.exe` 的进程，并且命令行里必须包含 `<启动器所在文件夹>\edge-profile`（开头清理）或本次的 `<…>\edge-profile-xxxxxxxx`（结束清理）这样一段完整路径。用户平时开的浏览器命令行里不会有这段路径。路径里 `launcher` 后面紧跟一个反斜杠，所以另一个叫 `launcher-xxx` 的文件夹也不会匹配。唯一的例外是：用户自己用 `--user-data-dir` 指向了 `launcher\edge-profile*` 下面的目录，那就是自找的。`CommandLine` 为空（别的会话、权限不够）的进程会被跳过，不会误杀，也不会清到。

**`AbandonedMutexException`：** 处理方式正确（见 §1 表）。

**`finally` 块的顺序（`:378-400`）：** 补启动 Claude → `Stop-Splash`（含一次 `Get-CimInstance`）→ 置前 Claude → 清理目录（至少睡 500 毫秒，最多重试 8 次）→ 释放互斥体。顺序合理，把"置前"放在慢清理之前是对的。小问题见 R-5（`Stop-Splash` 本身的耗时）和 R-10（淡出后到窗口被结束之间那一小段时间）。

**`IsIconic` 判断：** 正确。

**残留清理：** 逻辑完整；唯一的假设是"我们拿着互斥体，所以没有别的启动器在跑"，这个假设成立。

## 6. 发现

### 中

#### R-1　`found:` / `end:` 日志抓不到"窗口刚出现时"，诊断不了那次"窗口变大"（中）　【读代码】

- 位置：`launcher/launch.ps1:362`（`found`）、`:390`（`end`）、`:197-204`；README 的日志表（`README.md:102`）和 CHANGELOG 1.1.1 "新增"都写着 `found` 是"Claude 窗口刚出现时"。
- 问题：`Log-ClaudeRect 'found'` 只在播完动画之后的 `while (< 8 秒)` 等窗口循环里执行（`:361-362`）。如果 Claude 窗口在动画结束前已经出现（正常情况，动画有 9 秒多），循环的第一次检查就成功，`found` 记录的是**动画结束那一刻**的窗口；`end` 记录的是淡出结束（约 0.8 秒 + `Stop-Splash` 的耗时之后）的窗口。两行之间只隔 1–2 秒，所以几乎总是一样，**即使窗口在动画期间变了大小也一样**。
- 怎么验证（Windows）：关掉 Claude，用快捷方式启动，看 `launcher.log` 里 `found` 与 `splash placed` 之间隔了多久；预期是 `found` 的时间戳紧挨着 `splash reported DONE`。
- 建议：①在主循环里，第一次 `Get-TargetRect` 返回 `Source = 'claude'` 时记一行（真正的"刚出现"）；②之后 Claude 的矩形每次变化记一行，带时间戳、位置、大小、是否最大化（限频，比如每秒最多一行）；③顺便记下 Claude 窗口所在显示器的缩放比例，用来区分"Claude 自己改了窗口"和"坐标换算问题"。同时把 README / CHANGELOG 的说法改成与实际一致。
- 关于那次没查清的现象：我手头只有 CHANGELOG 里的两组数字（`26,5 1892×1132` → `1784×1075`）。两组数字的宽高比例不同（1.060 和 1.053），所以不像是同一个窗口被统一缩放读了两遍；这只是**推断**，不能据此下结论。对照 R-1 的日志就能看出是 Claude 自己调整了窗口，还是别的原因。

#### R-2　`last_rect.json` 作为"猜测"没有时效判断，过时的猜测会盖错区域（中）　【读代码 + 推断】

- 位置：`launch.ps1:156-161`（写入）、`:220-228`（读取顺序：真窗口 → 状态文件 → `last_rect.json` → 整屏）。
- 问题：`last_rect.json` 只在**启动器看得见 Claude 窗口时**才更新（`Save-Rect` 在 `:215`，只在 Claude 分支里调用），内容是"上次启动动画时 Claude 窗口的位置"。用户在两次启动之间移动、缩放、最大化 / 还原 Claude，它就过时了。它没有记录写入时间，也不在日志里写年龄。再加上 A5（状态文件任何原因读不到都是静默回退），"很久以前的最大化位置被当成现在的位置"这种情况会再次出现，混合缩放时更容易（状态文件的显示器匹配失败）。这次事故就是这么来的。
- 影响范围：只是**窗口出现之前**的那段时间画错（窗口一出现，跟随逻辑 `:341-342` 会重新对齐）。但那一段可能是几秒的整屏盖住，观感差。
- 建议（从保守到激进，我倾向 ①+②）：
  ① 写入时带上时间（`savedAt`），日志里的 `splash placed` 一行加上来源的"年龄"；超过一个阈值（比如 14 天，可调）就不再信任它，退到整屏或"等真窗口"。
  ② **只有"猜测"可用时，不要立刻把动画盖上去**：窗口保持不可见，等到 Claude 的真窗口出现（或等一个很短的上限，比如 1.5–2 秒）再显示；超时才用猜测。因为动画的前几百毫秒本来就是淡入，晚一点显示的代价很小，而画错的代价是整屏闪一下。**这需要在 Windows 上测量"页面就绪时间"和"Claude 窗口出现时间"哪个更早**（日志里都有时间戳），我无法验证。
  ③ 更激进：猜测的来源是 `saved` 时宁可盖整屏（和 `screen` 一致）。**不推荐**：整屏盖住一个只有半屏的应用，同样是错的。
- 另外：`Save-Rect` 第一次拿到有效矩形就立刻写（`$script:lastSaved` 初始为最小值，`:158`），而 Claude 窗口可能先以一个过渡尺寸出现，再调整到最终大小；之后每秒更新一次，最后一次写入在动画结束前约 1 秒内，所以最终存下的是接近最终的值，这一点没问题。

#### R-3　状态文件读取失败时没有任何日志，`SECURITY.md` 没跟上新位置（中）　【读代码】

- 位置：`launch.ps1:166-196`（`catch {}` 吞掉所有异常，找不到文件、解析失败、没有匹配的显示器三种情况都只是返回 `$null`）；`SECURITY.md:32`。

#### R-4　启动 Claude 之后不检查它是否真的启动了（A2 失效时无声失败）（低）　【读代码 + 推断】

- 位置：`launch.ps1:113`（`Start-ClaudeApp` 只记日志，`Start-Process` 立刻返回），`:359-365`（等窗口 8 秒，没找到只是继续）。

#### R-5　开头的残留清理无条件执行，给每次启动增加固定延迟（低）　【读代码；耗时大小未验证】

- 位置：`launch.ps1:248-250`。
- 问题：每次启动，在启动 Edge **之前**先同步执行一次 `Get-CimInstance Win32_Process`（WMI 查询，冷启动时通常要几百毫秒甚至更久）、再睡 300 毫秒、再扫描文件夹。而 Claude 要等 Edge 窗口出现后再过 800 毫秒才启动（`:351`），所以用户感觉到的"双击到 Claude 出现"的时间也相应变长。绝大多数时候没有任何残留。
- 怎么量（Windows）：看日志里 `--- launcher start`、`browser:` 两行的时间差。
- 建议：先用 `Get-ChildItem` 看有没有 `edge-profile*` 文件夹（几毫秒），**只有存在时**才查进程和睡 300 毫秒。`Stop-Splash` 在 `finally` 里也有同样的 `Get-CimInstance`（`:277,380`），会推迟"置前 Claude"和窗口被结束的时间，影响见 R-10。

#### R-6　互斥体的创建和等待没有兜底（低）　【读代码 + 推断】

- 位置：`launch.ps1:146-149`。
- 问题：`New-Object System.Threading.Mutex` 和 `WaitOne(0)` 如果抛出 `AbandonedMutexException` 以外的异常，脚本会以终止错误结束，**Claude 不会被启动**（这条路径在 1.0.1 加的 `finally` 兜底之外）。我能想到的一个情形：以管理员权限运行的启动器和普通权限的启动器同时存在时，后者可能没有权限打开已存在的同名互斥体（`UnauthorizedAccessException`，**推断**，默认的访问权限控制我没验证）。
- 建议：用 `try/catch` 包住整个互斥体逻辑，出错时记一行日志，当作"拿到了"继续，宁可偶尔两个启动器同时跑，也别让 Claude 打不开。

#### R-7　开始菜单里只有一个叫 "Claude" 的非 Store 条目时不会警告（低）　【读代码】

- 位置：`make_shortcut.ps1:64-68`。
- 问题：`$pick` 找不到 `Claude_*!*` 就退到第一个同名条目（`:66`），但警告只在 `$found.Count -gt 1` 时打印（`:68`）。如果开始菜单里只有一个叫 "Claude" 的条目，而且它是网页应用或别的东西，`config.json` 会写入它的 ID，且没有任何提示；而启动器后面又按 Store 版路径去找进程（A1）。
- 建议：只要选中的 ID 不符合 `Claude_*!*`，就打印警告（说明"这看起来不是 Microsoft Store 版"）。

#### R-8　脚本头部注释没跟上（低）　【读代码】

- 位置：`launch.ps1:11-14`，只列了三个来源（真窗口、`last_rect.json`、整屏），没有 `window-state.json`（实际顺序是真窗口 → 状态文件 → `last_rect.json` → 整屏）。

#### R-9　结束时无条件抢焦点（低）　【读代码】

- 位置：`launch.ps1:388`。
- 问题：动画有约 10 秒，用户可能已经切到别的程序在打字；动画结束时 `SetForegroundWindow` 会把 Claude 拉到前面。另外动画期间窗口是置顶的整块覆盖，也挡住了对 Claude 的操作（点击会跳过动画）。这是设计取舍，不一定要改；我只是提出来。
- 建议：如果当前前台窗口不是动画窗口也不是 Claude，就不抢焦点（只让 Claude 的任务栏图标闪一下），需要在 Windows 上试。

#### R-10　淡出完成后，窗口在被结束之前仍然盖着 Claude、会拦截点击（低）　【推断】

- 位置：`launch.ps1:367-380`。
- 问题：淡出结束时窗口透明度是 0，但窗口仍在、仍是置顶。以 `LWA_ALPHA` 设置透明度的分层窗口，鼠标点击仍然会被它接收（透明度不影响命中测试；没有设置 `WS_EX_TRANSPARENT`）。从淡出结束到 `Stop-Splash`（含 `Get-CimInstance`，R-5）把它结束，大约有 0.5–1.5 秒（耗时未验证）的时间，用户点 Claude 会点在一个看不见的窗口上。
- 建议：淡出开始前给窗口加上 `WS_EX_TRANSPARENT`（0x20，鼠标穿透），或者淡出一结束就先 `ShowWindow(SW_HIDE)` 再去清理。
